## Про «двойной запуск»

Отдельной классики на «решение проверяется двумя запусками» в открытом пуле
нет: жанр существует (рандомизация, адаптивные стратегии, задачи, где
 checker запускает программу дважды с разными входами), но чистой задачи
под него я не нашёл. Ближайшее по духу здесь — F: там решение обязано быть
устойчивым к случайности самой сетки, и это та же дисциплина мышления
(«оцени ожидание, не надейся на конкретный тест»).

## Баланс

- A–C — 20–40 минут: три разных интерактива, каждый со своим ограничением
  на число запросов.
- D–E — ядро: бинпоиск по префиксам и жадность по алфавиту.
- F–G — на дорешивание. F требует оценить, сколько запросов уйдёт в среднем,
  G — догадаться, что свойство должно быть локальным.

## Что обсудить после

1. A — почему `i` пилюль из `i`-й бутылки дают ответ одним числом
   (арифметическая прогрессия как «код»).
2. C — почему `2N` запросов хватает: `N` на чтение и не больше `N−1`
   на перестановку циклами.
3. F — почему при `p = 1/2` и 8-связности компонента почти наверняка
   большая, и почему BFS по ней не выходит за лимит запросов.
